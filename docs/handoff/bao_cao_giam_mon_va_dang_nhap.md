# Rest heavy props, harden ID login, chart usage

**Short version.** The picker should use a smooth weight, not a wall. Every món (object) keeps a full chance up to 500 lượt dùng (uses), the chance then halves for every further 300 uses (never below 0.05), a "speed" term nudges that by how fast the object reached its count, an optional hard stop H removes it entirely (H = 0 means never exclude), and a safety rule refills the pool if fewer than 100 candidates would remain. In a synthetic 1,533-object test, including the worst case where the free set was the 396 most-used objects, at least 394 stayed pickable. For login, both NIST and OWASP treat an identifier as something that is not proof of identity, so a 4-digit ID alone is a name tag and not a lock. With roughly 40 valid IDs among 10,000 possible values, a stranger needs about 250 guesses on average (the researchers' own arithmetic). The minimum safe design on FastAPI, Render and Neon is an allowlist, server-side sessions stored in Neon, a hardened cookie, a header-based CSRF check, admins taken from an `ADMIN_IDS` environment variable that fails closed when empty, and an append-only audit table. Adding a one-time invite link per person is the one change that turns "name tag" into real authentication, and it needs a policy decision from you. For the chart, use two plain linear bar views under one plain sentence: five ordered rows with a labelled "Ngưỡng 500 lượt" divider, and a sorted list of the heaviest objects with a dashed threshold line, built as real HTML so numbers are text. The weakest parts of this report are the formula defaults and the new-versus-old direction, which are the researchers' judgement and not from any source.

## Three kinds of evidence sit behind every claim

Each claim below is tagged by where it comes from. "Sources say" means a web page the researchers opened or a search result they read, with a link. "Inferred" means the researchers' own reasoning, arithmetic or design, with no source behind it. Three limits apply across the whole report. First, the login research read web pages through a fetch tool that returns model-written extracts, so quoted phrases from NIST, OWASP and others should be re-checked against the originals before you quote them in a policy document; this report paraphrases instead. Second, several sources were seen only as search-result summaries and are marked "summary only". Third, all code, thresholds and Vietnamese wording are untested proposals; the formula was run only on invented data, and no Vietnamese string has been read by a native speaker.

## Weights halve every 300 uses past 500 and the pool never empties

### Short answer

Use one formula in which the count decides whether an object is penalised and the speed of use decides how hard. Below 500 uses the weight is 1. Above 500 it is `0.5 ^ ((uses - 500) x m / 300)`, floored at 0.05, where `m` is a speed multiplier between 0.5 and 2. If a hard limit H is set (H > 0), an object with uses at or above H gets weight 0. If that would leave fewer than 100 candidates, the least-used excluded objects are put back at the floor weight. Picking is weighted random, so every non-excluded object stays possible and the soft penalty alone cannot shrink the pool.

### The formula and its defaults

```
age_days = (today - created_date).days
rate     = uses / max(age_days, 30)                 # uses per day since creation
m        = clamp( (rate / (500/365)) ** beta, 0.5, 2.0 )   # beta = 0 gives m = 1 (count only)
w        = 1                                          if uses <= 500
w        = max(0.05, 0.5 ** ((uses - 500) * m / 300)) if uses > 500
w        = 0                                          if H > 0 and uses >= H
chance of being picked = w / (sum of w over all free, eligible objects)
```

| Setting | Default | What it does |
|---|---|---|
| soft start | 500 uses | Penalty begins here; weight is exactly 1.0 at 500, so there is no cliff |
| half-life | 300 uses | Every 300 uses beyond the start halves the chance (500 is gentler, 200 harsher) |
| floor | 0.05 | Lowest weight of an object that is still eligible |
| hard limit H | 0 | 0 = never exclude; otherwise uses at or above H are excluded |
| beta | 0.5 | Strength of the speed term; 0 switches it off |
| m range | 0.5 to 2.0 | Caps how much speed can change the penalty |
| reference age | 365 days | "Normal" speed is reaching 500 uses in one year (about 1.37 uses per day) |
| age floor | 30 days | Stops a brand-new object from getting an absurd rate |
| minimum pool | 100 | Fewer candidates than this triggers the refill |

### Worked example (defaults, today 2026-11-11)

| Uses | Age (days) | Speed multiplier m | Weight, count only | Final weight |
|---|---|---|---|---|
| 1,587 | 120 | 2.00 | 0.081 | 0.050 (floor) |
| 1,083 | 850 | 0.96 | 0.260 | 0.273 |
| 892 | 200 | 1.80 | 0.404 | 0.195 |
| 600 | 100 | 2.00 | 0.794 | 0.630 |
| 600 | 800 | 0.74 | 0.794 | 0.843 |
| 500 | 60 | 2.00 | 1.000 | 1.000 |

Read the 892-use row: the object is 200 days old and has been used 4.5 times a day, so its excess over 500 counts 1.8 times as heavily and its weight falls from 0.404 to 0.195. That is lower than the 1,083-use object that took 850 days to get there (0.273). I re-checked these rows by hand and they match the researchers' script output. A hard limit of 1,000 would exclude the 1,587 and 1,083 objects; with H = 1,500 only 1,587 goes; with H = 0 nobody does. Those exclusion counts come only from the six top values you supplied (1,587, 1,083, 892, 825, 811, 786), so they are real, not simulated.

In plain Vietnamese for staff (draft, not native-reviewed): "Mỗi món có điểm cơ hội từ 0 đến 1. Đến 500 lượt dùng thì điểm là 1. Vượt 500 lượt, cứ thêm khoảng 300 lượt thì cơ hội giảm một nửa; món mới mà dùng rất nhanh thì giảm nhanh hơn. Nếu quản lý đặt mốc loại hẳn H thì món đạt mốc đó không được chọn nữa; H = 0 là không loại món nào."

### What the sources say

No source describes this exact problem, which is balancing the use of physical props. The closest established ideas come from search engines, ad servers, libraries and fleets, and they point the same way.

Search tooling already treats "free zone, then smooth decay" as a standard shape: Elasticsearch decay functions leave a value untouched inside an `offset`, then fall to a chosen score at a `scale` distance, and keep a separate hard `min_score` cut for the final score ([Elasticsearch function_score](https://www.elastic.co/guide/en/elasticsearch/reference/current/query-dsl-function-score-query.html)). Ad servers layer hard caps on top and let the stricter cap win ([Google Ad Manager](https://support.google.com/admanager/answer/9387317)). Libraries and fleets treat a threshold hit as a candidate for human review rather than automatic retirement: CREW library weeding formulas use age and non-use screens ([LILI](https://www.lili.org/forlibs/ce/able/course4/06criteriaage.htm)), and fleet guidance says fixed age or mileage triggers ignore condition differences and should only flag units for checking ([Automotive Fleet](https://www.automotive-fleet.com/articles/how-to-calculate-optimal-replacement-cycles)). Together these support a soft ramp plus an optional hard cap, which is what the formula does.

Count is the better primary signal because wear is usually counted in accumulated use. Fleet managers describe engine hours as the closest proxy for wear ([HAPN](https://gethapn.com/blog/equipment-utilization-tracking/)), and Apple rates batteries in charge cycles ([Apple Support](https://support.apple.com/en-us/102888)). A weighted random pick, in which each object's chance is proportional to its weight, is a standard technique ([wrswoR reference](https://cran.r-project.org/web/packages/wrswoR/refman/wrswoR.html), implementation docs only).

Two warnings from the recommender literature shaped the design. A strong correction can oscillate while a weak one converges smoothly but slowly ([FairCo](https://arxiv.org/abs/2005.14713)), which argues for a gentle half-life and a floor. And cutting popularity too hard costs usefulness: a survey of popularity-bias methods reports users wanted only a light bias, and that reducing popularity does not automatically improve quality ([Klimashevskaia et al.](https://arxiv.org/html/2308.01118v3)). Variety-focused re-rankers such as MMR solve a different problem (variety inside one selection) and at Airbnb added friction through over-diversifying ([Airbnb, arXiv 2004.02621](https://arxiv.org/abs/2004.02621)), so the notes left them out.

On the pool-size guard, recommendation widgets run fallbacks in a fixed order whenever the earlier step returns fewer items than needed ([Visually.io fallback logic](https://help.visually.io/merchandising-fallback-logic), vendor docs, summary only), and a feed-ranking patent applies its discounting only partially so the candidate list is not emptied ([US12182138B2](https://patents.google.com/patent/US12182138), the applicant's own claims). No source gives a standard minimum pool size; the figure of 100 is the researchers' placeholder.

### What the researchers inferred

The soft penalty cannot starve the pool because every eligible weight stays at least 0.05, and only the hard limit or weight 0 removes an object; this is arithmetic, not a finding. On an invented 1,533-object pool (only the top six counts are real), across 5,000 random free sets of 396 objects the candidate pool was 394 to 396 with H = 1,000 and the refill never fired. In the worst case, where the free set is the 396 most-used objects, 394 candidates remained at H = 1,000 and 395 at H = 1,500. In a deliberately extreme test (H = 150) 310 objects were excluded, 14 were put back, and the pool landed on exactly 100. The heavy objects (7 of 396, over 500 uses) received 1.21% of 200,000 simulated picks against 1.77% of the set, so at pool level the soft penalty is gentle by design.

A second inference matters for the future: the 500 threshold is an absolute number, and counts only rise. Sooner or later most of the pool will sit above it. The notes suggest reviewing the threshold periodically or defining it as a percentile; this is the researchers' idea, not a sourced practice.

### What is uncertain

The new-versus-old direction is the least supported choice. No source in any domain decides whether an object that reached a high count fast should be rested more or less than one that got there slowly. The sources that measure wear in hours or cycles imply that equal count means roughly equal wear regardless of age. The researchers chose to penalise fast accumulation more, on the reasoning that a fast-rising object is being over-picked right now and rest or balancing is the goal; a fleet-telematics vendor makes a similar balancing claim but gives no numbers ([Geotab](https://www.geotab.com/blog/maintenance-scheduling-for-off-road/), summary only). The counter-argument is real: an old object that reached the same count slowly has also aged longer and may be nearer wear-out, in the language of the bathtub curve ([NIST handbook](https://www.itl.nist.gov/div898/handbook/apr/section1/apr124.htm)), so some would penalise it more. Set beta to 0 if objects degrade by calendar age as well as by use. The speed term also cannot see recent bursts or long idle periods, because only lifetime count and creation date exist; a last-30-days count would be a better signal if the tool starts saving periodic snapshots. Raw rates are unstable for young objects, which is why the age floor and the 0.5 to 2 cap exist ([Wheeler on small denominators](https://andrewpwheeler.com/2018/07/23/sorting-rates-using-empirical-bayes/)).

Every default (half-life 300, floor 0.05, beta 0.5, 365-day reference, minimum pool 100) is a design choice with no calibration. The earlier note on popularity penalties used a half-life of 500 as an illustration; treat 200 to 500 as the tuning range. The speed term changes individual weights a lot but the pool only slightly: in the synthetic data the "medium" band held 6 objects with the term on and 4 with it off. The real unknown is how many of your 1,533 objects are above 500, 600 and 800, because that number decides whether a hard limit near 500 could ever bite. The chart in section 4 answers that question. Finally, the "minimum pool 100" is not tied to how many props one box needs, which the notes do not state.

## An ID is a name tag, so fence it and add a device link

### Short answer

ID-only login can attribute actions among colleagues who play fair, and an allowlist keeps out IDs that are not on the list. It cannot stop anyone who knows or guesses a valid ID from becoming that person, and "admin by ID" means anyone who learns an admin's ID is an admin. Rate limiting only slows the guessing. The minimum safe design is therefore the set of controls in the table below, plus one decision for you: allow a one-time invite link per person (the researchers' recommendation), or accept ID-only and label it honestly as attribution. The only mid-way option, a self-chosen PIN of at least 6 digits, may clash with your "no passwords" policy.

### What ID-only login can and cannot protect

NIST defines authentication as proving control of an authenticator, and says the identifier is a separate thing that may even be pseudonymous ([NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)). OWASP says the same and adds that user IDs should be random because predictable or sequential ones can be inferred ([OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)). A 4-digit company ID is small, often sequential and known to colleagues. NIST requires look-up and out-of-band secrets to be at least six decimal digits, and longer for passwords, so a 4-digit value sits below every NIST floor. The researchers inferred that ID-only login therefore does not meet even NIST's lowest assurance level, and that neither standard describes an "identification-only" tier, so you should not claim compliance with either.

The practical consequence, from the researchers' arithmetic: with about 40 allowlisted IDs among 10,000 possible values, a random guess hits a valid one about 0.4% of the time, around 250 guesses on average, and far fewer if IDs cluster in a range. Uniform error messages cannot hide this, because a successful login is itself the signal that the ID is valid. Shoulder-surfing is mostly irrelevant when IDs are on badges and org charts; the realistic risks are a colleague typing someone else's ID and two people sharing one ID, which destroys attribution whatever the technology.

### Where an extra secret helps most

Rate limits, allowlists and uniform responses reduce noise but do not add an authenticator. OWASP names multi-factor authentication as the best defence against password-style attacks and warns that IP blocking alone is easy to evade ([OWASP Credential Stuffing Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html)). The researchers compared the options for a 15-to-40-person team:

| Option | What it buys | Cost | Verdict (researchers' judgement) |
|---|---|---|---|
| ID-only plus allowlist, throttling, audit, warning banner | Strangers with unknown IDs rejected; every action attributed to an ID | Zero user friction | Acceptable only for low-value data where nothing binding is approved |
| ID plus one-time invite link per person, redeemed once per device, then a long-lived HttpOnly cookie | A 128-bit secret a stranger cannot guess; the ID becomes just a label | Admin issues and re-issues about 15 to 40 links; token table with hashed, expiring, single-use tokens | Recommended minimum if the tool records who approved what |
| ID plus self-chosen PIN of 6 or more digits, blocklisted, hashed | A per-person secret, no admin work | Users must remember it; may conflict with "no passwords" | Next best if the policy allows memorised secrets |

Human-chosen 4-digit codes are very predictable: in about 3.4 million leaked 4-digit passwords, 1234 alone was 10.7% and a third of codes fell within 61 guesses ([DataGenetics](http://www.datagenetics.com/blog/september32012), a leaked-password proxy for PINs). That is why a PIN would need a blocklist and a longer length. The invite-link design follows OWASP's token rules (random, single-use, expiring, hashed, rate-limited, no-referrer on the landing page) from the password-reset sheet ([OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)); OWASP does not cover invitations specifically, so this reuse is an inference. Whether a link or a PIN counts as a "password" under your policy is your call; NIST files a numeric PIN with memorised secrets ([NIST](https://pages.nist.gov/800-63-4/sp800-63b.html)).

### The minimum checklist for this stack

| Area | Setting | Basis |
|---|---|---|
| Sessions | Random 256-bit token (`secrets.token_urlsafe(32)`), only its SHA-256 hash stored in a Neon table; no signing secret needed; new token at every login; logout deletes the row | OWASP says a fast hash is enough for high-entropy verifiers ([OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)) and Python docs say 32 bytes suffices ([Python secrets](https://docs.python.org/3/library/secrets.html)); skipping the signing secret is the researchers' conclusion |
| Why not signed cookies | Starlette's `SessionMiddleware` needs a `secret_key` and stores data client-side ([Starlette](https://www.starlette.dev/middleware/)); it cannot be revoked server-side | Researchers' reasoning |
| Cookie | `HttpOnly; Secure; SameSite=Lax; Path=/`, no Domain, named `__Host-sid` in production | MDN cookie rules ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)); OWASP prefers Strict but accepts Lax; Lax chosen by researchers so links opened from chat keep the login |
| Timeouts | Idle and absolute limits enforced on the server; researchers suggested 12 hours idle and 7 days absolute | OWASP examples are 15 to 30 minutes idle and 4 to 8 hours absolute for an all-day office app; NIST's lowest level allows up to 30 days. The researchers' values are longer than OWASP's examples, so decide deliberately |
| Where state lives | Sessions, throttle counters and audit rows in Neon, never in memory | Render Free spins down after 15 idle minutes, may restart at any time, and has an ephemeral disk ([Render Free](https://render.com/docs/free)) |
| CSRF | Refuse state-changing requests unless `Sec-Fetch-Site` is `same-origin` or `none`, or `Origin` matches; refuse if a session cookie arrives with neither header; no state change on GET; no permissive CORS | OWASP calls Fetch Metadata reliable but says an Origin fallback is mandatory and missing headers are not proof of same-origin ([OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)); `Sec-Fetch-Site` cannot be set by page scripts ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site)) |
| Roles | Compute "is admin" from `ADMIN_IDS` on each request; `require_admin` on every `/api/admin/*` route; sync-token routes on their own router that never reads cookies | FastAPI router-level dependencies ([FastAPI](https://fastapi.tiangolo.com/tutorial/bigger-applications/)); design is the researchers' |
| Static files | Do not mount the whole front-end folder; serve `admin.html` through an explicit route | A `StaticFiles` mount bypasses route dependencies, per one community thread ([FastAPI issue 858](https://github.com/fastapi/fastapi/issues/858)); the page is hidden for convenience, the API check is the real wall |
| Rate limiting | Database table keyed by ID, by IP and one global breaker; progressive delay, not hard lockout | OWASP warns lockout can be abused for denial of service ([OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)) and that per-IP limits are easy to evade; with ID-only login, a per-ID counter does little because a valid guess succeeds on the first try, so the global breaker is the only control that does not need a trustworthy IP (researchers' reasoning) |
| Audit | Append-only `audit_log` (time, actor, action, box id, changed fields, IP) written in the same transaction as the change, plus `created_by` and `updated_by` on boxes; actor comes only from the session, never from the request body | OWASP Logging lists when, where, who and what, plus authentication and user-administration events ([OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)); Render logs last only 7 days on the Hobby plan ([Render logs](https://render.com/docs/logging)), so the database is the audit store |

A record made under an ID proves that this ID acted, not that this person did. The notes recommend saying so on the approval screens ("approved under ID 1234") and wording the login page honestly. A draft the researchers proposed, with my Vietnamese rendering (not native-reviewed): "Enter your company ID so we can record who made or approved each box. This is a name tag, not a lock." / "Nhập mã công ty để hệ thống ghi lại ai đã làm hoặc duyệt hộp. Đây là thẻ tên, không phải khóa."

### Admin bootstrap on an empty database

Set the first admins through an `ADMIN_IDS` environment variable in the Render dashboard, read at startup, and fail closed if it is empty and no admin exists: show a static "setup required" page and refuse all logins. Real precedent argues against the alternatives. In 2017 attackers ran thousands of automated scans a day against unfinished WordPress installs, completed the setup themselves and took over the host ([Security Affairs](https://securityaffairs.com/wordpress/60981/hacking/wordpress-wpsetup-attack.html)); Portainer's fix is to stop listening after 5 minutes without an admin ([Portainer docs](https://docs.portainer.io/sts/faqs/installing/i-just-installed-portainer-but-i-cant-access-the-ui-how-do-i-fix-this)). First-come registration and "open until set, with a warning" are therefore unsafe on a public URL. A one-time code printed in the logs is a recognised pattern in small projects ([Oore](https://oore-docs.pages.dev/reference/cli/oore-setup)) but is weaker here: the code regenerates after restarts, logs expire, and anyone who can read the Render logs can claim admin. Because an admin is just an ID in a list, the notes advise requiring the invite-link step on admin devices.

### What is uncertain

The Render client IP is not settled. A 2021 Render feedback thread contains one user's claim that Render appends to a client-supplied `X-Forwarded-For` and a staff reply that the first entry is the real client IP ([Render feedback](https://feedback.render.com/features/p/send-the-correct-xforwardedfor)), while a third-party write-up says the header is trivially spoofable ([Rails-on-Render article](https://rohitpaulk.com/articles/render-rails-remote-ip)); neither is official documentation, and Render's own pages say nothing on the subject. Test with a forged header on the live service before relying on any per-IP limit. Uvicorn trusts forwarded headers only from `127.0.0.1` and `::1` by default ([Uvicorn settings](https://uvicorn.dev/settings/)).

Other gaps from the notes: it is unknown whether the existing Tampermonkey and Apps Script sync calls carry `Origin` or `Sec-Fetch-Site` headers, which decides how they pass the CSRF check; whether Render passes the `Host` header unchanged was not confirmed; who may read Render logs, whether changing an environment variable restarts the service, and Neon's backup and retention limits were not checked; the code sketches are untested; the throttle numbers (for example 5 failures per 10 minutes) are starting suggestions; NIST's section on sessions was only partly readable; and no usability study of invite links versus PINs for non-technical staff was found. Audit retention and legal weight of ID-attributed approvals depend on company policy, which the notes did not research.

## Two linear bar views and one sentence carry the warning

### Short answer

Put one plain sentence at the top of the warning panel, then two linear-scale views as real HTML. First, five ordered rows (Dưới 100, 100 đến 249, 250 đến 499, 500 đến 999, Từ 1.000 trở lên), each with its count printed beside a bar, and a single dashed divider row labelled "Ngưỡng 500 lượt" between the 250-to-499 and 500-to-999 rows. Second, a sorted horizontal list of the heaviest 5 to 10 objects with a dashed vertical line at 500, labelled "Ngưỡng 500". Do not use a log axis, a Pareto line with a second axis, or touching columns on a numeric axis.

### Why this shape

The five bands have unequal widths, so drawing them as touching columns invites readers to judge area instead of height; treating them as ordered rows removes the problem, and the 500 threshold coincides with a band edge, so one divider row does the job with no axis (the researchers' reasoning). Sorted bars are the standard ranking form ([FT Visual Vocabulary](https://github.com/Financial-Times/chart-doctor/blob/main/visual-vocabulary/README.md)), and a line or range is a common way to mark a threshold on a bar chart ([Datawrapper](https://www.datawrapper.de/blog/annotations-in-bar-charts)). Log axes are the main trap: in a 2023 study of 99 students, 42% read a log-axis chart correctly against 86% on a linear axis, and 52% of the log group treated log spacing as linear ([Melnik-Leroy et al.](https://www.frontiersin.org/articles/10.3389/fpsyg.2023.1125810)); the European Commission guide offers a counter-view for Covid-era audiences ([data.europa.eu](https://data.europa.eu/apps/data-visualisation-guide/logarithmic-scales)), but your audience is explicitly non-technical. A Pareto chart is a dual-axis chart, which Datawrapper says must be extremely well designed for a mainstream audience ([Datawrapper](https://www.datawrapper.de/blog/dual-axis-charts-guide)), and it answers "how concentrated is use" rather than "how many are over 500"; one sentence ("6 món dùng nhiều nhất chiếm X phần trăm tổng lượt dùng") covers concentration if you need it.

The honest linear picture is itself the message: a handful of thin bars beside a huge one shows that few objects are over the threshold. Because 2 objects against 1,210 would be a 0.17% sliver, roughly half a pixel on a phone, the printed count, the divider row and a 4 px minimum bar carry the meaning. Cutting the longest bar with a break mark would make small bars readable but breaks proportionality, and no source endorses it for lay readers, so treat it as an open design decision.

### The sentence and the order of the panel

Lead with a visually hidden "Cảnh báo: " prefix for screen readers, then one fact and no adjectives: "Có 46 trong 1.533 món đã dùng từ 500 lượt trở lên." (46 is a placeholder.) GOV.UK's warning-text pattern uses the same hidden-label idea and marks the icon `aria-hidden` ([GOV.UK](https://design-system.service.gov.uk/components/warning-text/)). W3C advises summarising a complex graphic in the surrounding text and showing the long description as part of the main content ([W3C WAI](https://www.w3.org/WAI/tutorials/images/complex/)); here the visible table is the long description, so there is nothing hidden to keep in sync. Compute the over-threshold count once and use it for the sentence and the chart, with a test that the over-threshold band rows sum to it. Do not use `role="alert"` for text that is present on page load. "Khoảng 3 trong 100 món" is an optional second sentence; natural-frequency wording helped comprehension in a 2023 review of 35 studies, but that evidence is from a search snippet, rated moderate and partly disputed ([review table](https://health-policy-systems.biomedcentral.com/articles/10.1186/s12961-023-01017-2/tables/1)).

### Accessibility choices

WCAG says colour cannot be the only way information is conveyed ([WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)), graphics needed to understand a chart need 3:1 contrast ([WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)), text needs 4.5:1 ([WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)), and content must work at 320 CSS pixels without two-way scrolling ([WCAG 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)). The researchers' own contrast calculations (not from a source) found your brand orange #f0691a is only about 2.9:1 on the assumed light panel colour #fbf8f3, so it fails for anything meaningful; a darker orange #b8430a reaches 5.2:1 and blue #2f6fa0 reaches 5.1:1. Those two have almost the same lightness, so they look identical in grayscale or to some colour-blind readers. The over-threshold group is therefore marked four ways: diagonal hatch, a darker-orange outline, the divider row label, and the printed number. Brand orange stays decorative only.

Build the chart as a real `<table>` and an ordered list, with the bars as `aria-hidden` decoration beside text numbers. That gives screen-reader users row and column navigation for free, scales with browser zoom, and avoids the situation where an image role hides every number. Keep table cells at their default display, because changing `display` on table parts has broken screen-reader table semantics in several browsers ([Roselli](https://adrianroselli.com/2022/07/its-mid-2022-and-browsers-mostly-safari-still-break-accessibility-via-display-properties.html)). Add no animation by default and gate any grow-in behind `prefers-reduced-motion: no-preference` ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)). Use `Intl.NumberFormat('vi-VN')`, which prints 1533 as 1.533, and match the rest of the page ([W3C i18n](https://www.w3.org/International/questions/qa-number-format)). Write it by hand, about 120 lines of vanilla JavaScript using `textContent` only, since object names are data. A canvas library such as Chart.js leaves accessibility to the author ([Chart.js docs](https://www.chartjs.org/docs/latest/general/accessibility.html), excerpt only), and the researchers saw Highcharts' strong accessibility module but reported commercial licence terms from summaries only.
